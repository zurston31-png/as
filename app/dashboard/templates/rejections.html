Why, by stage

Mints is how many distinct tokens a reason stopped. Events is how many times it fired. When events greatly exceed mints, one token is being re-evaluated rather than many tokens failing — the “per mint” column makes that visible instead of letting it inflate the ranking.

Near misses

Rejections within {{ near_miss_points }} points of the configured threshold. A gate that rejects candidates far below its line is discriminating; one whose rejections cluster against the line is closer to a coin flip. This is an observation about the score distribution, not a reason to move a threshold — whether the rejected tokens would have made money is a forward-return question, and it is answered on the research page, not here.

How to read this

The stage that stops the most candidates is nearly always the earliest one, because it is the only stage that runs on everything. That is arithmetic, not evidence that it is set too strictly.

This page answers where candidates are lost. It cannot answer whether losing them was right — that needs the forward returns of the tokens each filter rejected, compared against the ones it passed, which is what app/analysis/filter_quality.py measures and the research page reports once enough outcomes have been collected.
